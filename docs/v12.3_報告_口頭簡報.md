## 1. 進度：四條線的收斂狀態

四條線的定義與報告庫的 2026-09-13 週報表 6-1、成果總覽 `SUMMARY.md` 相同。

| 線 | 結論 | 依據 |
| --- | --- | --- |
| **模型端** | 連續四輪、十一種改動全部無效 | v9 六臂消融零臂通過 2σ 門檻；v12s 放大 3.84 倍參數只換到 +0.003 |
| **訓練協定** | 有效，但修的是可報告的評估精度 | 固定輪數並報 `last.pt`，valid 可與 test 併計，逐類 ±2SE 最差值 0.140 → 0.099 |
| **部署端** | 662 不採用；**天璣 8300 平板、Snapdragon 8 Gen 2 手機在 320 成立** | 高階裝置 `fp32@320` 連續跑 38.4 / 29.8 FPS，下一個解析度被持續負載擋下——從「不採用」變成「**分裝置**」 |
| **資料端** | 外部影像無效；重標有效但**未讓模型變好** | 外部影像 +0.021；重標後八類平均 −0.002；工作包 A、B 都已結案 |

四條線都被預先登記的判準關閉；兩個有效的手段修的是「數字能不能被相信」，**沒有一個讓模型變好**。

## 2. 本期回答的七個問題（併成五列）

**每一個的標準都寫在量測之前**，沒有一個是看完結果才決定怎麼算。兩輪標註、兩台高階裝置各併成一列，與報告庫週報表 1 的七列是同一組問題。

| 問題 | 事先寫好的標準 | 結果 | 所以 |
| --- | --- | --- | --- |
| 662 上要不要做即時辨識 | 每張 ≤ 40 ms（25 FPS）**且**精度 ≥ 0.764 **且**沒有一類掉超過 0.10 | 速度全過、**精度全不過** | 662 只做拍照辨識 |
| 薊馬葉害的框能不能畫得一致 | 兩人重疊度中位數 ≥ 0.85 | 0.746 → **改規則後 0.899** | 類別保留，全類重標 |
| 外部潛葉蛾照片有沒有用 | 潛葉蛾 AP50 要多 0.04 以上 | **+0.021** | 無效，不交付 |
| 重標能不能解除薊馬葉害的矛盾 | valid 與 test 差距 < 0.165 | −0.202 → **+0.121** | 三輪不收斂的問題解除 |
| 高階裝置上能不能做即時辨識 | 前面三條，**再加「連續跑也要 ≤ 40 ms」**；兩台用同一份標準 | **兩台都是 320 過**（平板 38 FPS、手機 30 FPS）；平板 512、手機 416 連續跑不過 | 只到 320 |

### 2.1 值得多講一分鐘：為什麼 0.861 不是進步

- v5.7 的 test mAP50 是 **0.861**，v11.5 是 **0.810**，看起來進步了 0.05。**不是。**
- 新規則讓薊馬葉害的框變大 1.36 倍，而 AP50 只要重疊 ≥ 0.5 就算對——**框愈大愈容易算對**。
- 把薊馬葉害拿掉、只看標註沒變的八類：**0.8527 → 0.8508，等於沒變**。
- 所以要報 0.861 時，一定要同時說「新標註約定下、不能跟舊數字比」。

### 2.2 值得多講一分鐘：為什麼要量「連續跑」

- **平板**：512 解析度短時間量是 **25 FPS**，剛好過線。連續跑的**頭 30 秒**，表面溫度就從 35 °C 升到 47 °C、開始降頻，之後只剩 **16 FPS**。
- **手機**：416 解析度短時間 **28 FPS** 過線。它沒有過熱，但連續跑到第 3 段就整段掉到另一個檔位，之後只剩 **19–20 FPS**。
- **662**：反過來，**連續跑 10 段完全沒變慢**，一直是 16 FPS——只是本來就太慢。
- **三台放在一起**：跑得越快的晶片，連續跑掉得越多（平板 1.6–1.7 倍、手機 1.05–1.4 倍、662 不掉）。
  **只看短時間的數字，會以為高階機的下一個解析度也可以做即時辨識**。
- 換成畫面感受：相機預覽每秒最多 30 張。平板 320 的 38 FPS 每一張都跟得上，手機 320 的 30 FPS 幾乎每一張都跟得上；
  平板 512 的 16 FPS、662 的 16 FPS 大約每兩張只辨識一張。

## 3. 要在這場會議上決定的三件事

### 決策 1：App 要不要依裝置等級開放即時辨識？

| 選項 | 代表什麼 | 還需要做什麼 |
| --- | --- | --- |
| **做** | 高階裝置開即時辨識（320），其他裝置只做拍照辨識 | 決定怎麼界定「高階」——662 與這兩台之間的中階裝置沒有量，界線在哪裡不知道 |
| **不做** | 全部只做拍照辨識 | 無；三台的結果寫進報告，當作各等級裝置的實測上限 |

### 決策 2：拍照模式可以接受多久出結果？

有了這個上限，才能在 `fp32@320`、`fp32@640`、`w8a32@640` 之間選。選定之後只需要把 v5.7 的權重重新匯出那一個組合。

### 決策 3：剩下的時間要不要繼續追模型精度？

- 工程手段已經用盡：改架構、放大模型、調匯出參數、加外部照片，全部量過都沒用
- 剩下有依據的只有兩件：量**介殼蟲**的框一致性（兩人各半小時），或**補拍同域照片**（約 353 張）
- 不追的話，剩下的時間用來收尾文件與報告

## 備答：可能會被問到的

| 問題 | 一句話回答 |
| --- | --- |
| **0.861 比 0.810 高，是不是進步了？** | 不是。框定義換了，框變大就容易算對；標註沒變的八類平均是 −0.002，等於沒變 |
| **那為什麼要換成 v5.7？** | 舊的薊馬葉害框彼此矛盾，那個類別的數字量到的是標註噪聲；換了之後數字才有解釋力 |
| **為什麼不直接刪掉薊馬葉害？** | 它是唯一符合田間場景的薊馬訊號，刪掉數字也不會變好；改規則重測一次就通過了 |
| **外部照片為什麼沒用？** | 那批是摘下的葉子放白紙上拍，跟田間照差很多，而且 124 張只來自約 20–25 片葉子；加了資料的潛葉蛾，動得跟完全沒加資料的油斑病一樣多 |
| **兩台高階機都過了，是不是可以做即時辨識？** | 只到 320，而且各只有一台；中階裝置沒有量，界線在哪裡不知道 |
| **手機 30 FPS 比平板慢，為什麼也算過？** | 標準是 40 ms（25 FPS）；手機連續跑最慢的一段是 33.5 ms，還有 6.5 ms 餘裕 |
| **8 Gen 2 不是比天璣 8300 強，為什麼手機比較慢？** | 這支手機閒置時 CPU 頻率上限就被壓在一半左右，來源沒查到；我們照出廠狀態量，不改系統設定，所以結論只代表這支手機 |
| **短時間已經過線，為什麼算不行？** | 即時辨識是一直在跑的；平板 30 秒內就降頻，手機跑到第 3 段就掉檔，連續跑都超過 40 ms |
| **662 連續跑會不會更慢？** | 不會。補量時連續跑 10 段都在 63 ms 左右、完全沒變慢；只是本來就只有 16 FPS，離 25 FPS 差太遠 |
| **662 的舊數字只量一輪，可信嗎？** | 用跟另外兩台一樣的方法（3 輪交錯）重量過了，8 個檔案差距都在 ±3.1% 以內，結論不變 |
| **GPU 跑 640 只要約 31 ms，為什麼不用？** | 只在兩台高階機上成立，662 整張交給 GPU 也沒變快；而且只量了一輪、沒有連續跑，後處理成本也沒量，要另外登記一份計畫再量 |
| **662 的結論會改嗎？** | 不會。662 的問題是晶片速度，換模型、調參數、用 GPU 都補不上 |
| **還有辦法讓模型更準嗎？** | 不拍照片的前提下沒有了；剩下量介殼蟲的標註一致性，或補拍照片 |
| **這些判準是不是看完結果才訂的？** | 不是。每一份判準都比量測早 commit，時間可以從 git 紀錄查到；途中補定的細節、662 的補量協定也都在對應量測之前 commit；標註門檻 0.85 登記在 2026-08 的 v11 計畫書，兩臂門檻 0.04 與 0.165 登記在訓練前的驗收文件 |
