## 0. 結論先講

- **三台的判定**：Snapdragon 662 **不成立**（fp32 在 320 以上全部超過 40 ms）；天璣 8300 平板與 Snapdragon 8 Gen 2 手機**成立，都只到 320**。
- **補量沒有改變任何數字的量級**：662 用 3 輪交錯重量後，8 個檔案與 v12.1 的舊數字差距都在 ±3.1% 以內。
- **平板比 662 快 4.3–4.5 倍、各解析度幾乎一致**（純算力差）；**手機比 662 只快 2.1–3.2 倍、而且解析度越低賺越少**
  ——手機的 320 被算力以外的因素卡住（§2.2）。
- **連續跑掉多少，跟晶片快慢剛好相反**：平板持續是突發的 1.58–1.72 倍（半分鐘內降頻）、手機 1.05–1.40 倍、
  **662 是 0.94 倍——10 段完全沒有衰減**，機殼只從 32 °C 升到 40 °C，CPU 降頻裝置全程在 0 檔。
- **GPU 的分水嶺是 end2end，而且只有高階機受惠**：end2end 關時三台都能把 511 個節點全交給 GPU，
  640 在平板 31.8 ms、手機 30.6 ms（CPU 的 0.52／0.37 倍）；**662 整張交給 Adreno 610 仍是 CPU 的 0.91–1.18 倍，沒有變快**。
- **`fp32@416` e2e0 的 GPU 初始化在三台都異常**：手機要 21.3 秒（其他組合 1–5 秒），662 與平板在 45 秒的等待內沒有完成。
- **NNAPI 三台都不用**：662 與手機只有 Android 內建的參考實作、沒有生效；平板交給 MediaTek 加速器反而慢 1.7–5.4 倍。

## 4. GPU delegate

各只量 1 輪。

| 組合 | 節點替換 | 平台 1 (ms) | 平台 2 (ms) | 平台 3 (ms) | GPU ÷ CPU：1／2／3 |
| --- | --- | ---: | ---: | ---: | --- |
| `fp32@320` e2e0 | 511/511 | 76.14 | 11.59 | 18.56 | 1.18／0.80／0.64 |
| `fp32@320` e2e1 | 54/559 | 67.43 | 29.44 | 28.06 | 1.01／1.96／0.90 |
| `fp32@416` e2e0 | 511/511 | **無結果** | **無結果** | 20.73（初始化 21.3 秒） | —／—／0.43 |
| `fp32@416` e2e1 | 54/559 | 124.64 | 37.44 | 34.58 | 1.13／1.46／0.98 |
| `fp32@512` e2e0 | 511/511 | 152.84 | 21.50 | 21.25 | 0.91／0.56／0.35 |
| `fp32@512` e2e1 | 54/559 | 174.38 | 49.54 | 54.90 | 1.02／1.26／1.04 |
| `fp32@640` e2e0 | 511/511 | **282.00** | **31.82** | **30.60** | **1.05**／**0.52**／**0.37** |
| `fp32@640` e2e1 | 54/559 | 280.63 | 72.06 | 79.74 | 1.05／1.15／0.94 |

GPU ÷ CPU 以各平台的 CPU 3 輪最小值計（不含 2 ms 保留）。

1. **end2end 決定 GPU 能不能整張接手，三台一致。** 開著時偵測頭的 `ADD`（版本 4）、INT64 `CAST`、`GATHER_ND` 等算子不被支援，
   只剩 54/559 個節點上 GPU；關掉就是 511/511。
2. **整張交給 GPU 之後，只有高階機變快。** 662 的 Adreno 610 整張接手是 CPU 的 0.91–1.18 倍；
   唯一低於 1 的 512 e2e0（0.91）落在 CPU 三輪的散佈（167–192 ms）之內，不算變快。
   平板與手機的 640 都降到約 31 ms，是三台所有數字中**唯一「精度最高又在 40 ms 內」**的組合。
3. **GPU 初始化**：662 的 e2e0 要 5.3–6.0 秒、e2e1 約 2.0–2.2 秒（CPU 只要 0.06–0.19 秒）。
4. **`fp32@416` e2e0 的 GPU 初始化在三台都異常。** 662 的 log 停在「Loaded OpenCL library」、45 秒內沒有進到「Initialized OpenCL-based API」；
   平板同樣無結果（log 已被覆寫）；手機雖然有結果，初始化卻要 21.3 秒，是其他組合的 4–20 倍。
   同一個檔案在三台都出問題，**較可能是這個檔案的 GPU 核心編譯特別慢，而不是裝置問題**——但沒有加長等待時間重量，**未證實**。
5. **仍不構成判定**：只量 1 輪、沒有持續負載、GPU 管線的後處理成本沒有量。要採用必須另開一份登記。

## 5. NNAPI

| 平台 | 可用的加速器 | 結果 |
| --- | --- | --- |
| 平台 1 | 只有 `nnapi-reference`（Android 內建的 CPU 參考實作） | **未生效**，8 個檔案全部由 XNNPACK 在 CPU 上執行，數字等同 CPU 再量一輪（320 e2e0：63.73 對 CPU 64.61 ms） |
| 平台 2 | MediaTek 加速器（`mtk-neuron`、`mtk-mdla`、`mtk-dsp`） | 接走 88–99% 的節點，**卻比 CPU 慢 1.7–5.4 倍**，初始化 11–16 秒 |
| 平台 3 | 只有 `nnapi-reference` | **未生效**，數字等同 CPU 再量一輪 |

原因兩種、結論一種：**這個模型的 fp32 圖不走 NNAPI**。NNAPI 自 Android 15 起也已被標為淘汰。

### 6.1 補量協定（2026-09-13 登記，早於任何補量）

使用者同意補量 1、2、3（批次超過 5 個模型、GPU／NNAPI、持續負載的非標準參數三項一併確認）。協定與平台 2、3 逐字相同：

| 順序 | 內容 | 指令 |

## 7. 限制

1. **每個平台只有一台裝置**：平台 2 是平板（散熱較好）；平台 3 的 CPU 頻率上限在閒置時就被壓低、來源未查明。
2. **三台的溫度感測器不同**（平台 1 是 sysfs 的 `shell_*`，平台 2、3 是 HAL 的 SKIN／skin），表面溫度的絕對值不能互比。
3. **三台量測時都在充電**，電量與起始溫度各不相同（§1）。
4. **GPU 與 NNAPI 各只量 1 輪**；持續負載只量了計畫指定的組合。
5. **在平台 1 與平台 3，突發的 3 輪最小值不一定是下限**：662 連續跑比它快，手機的三輪可差到 1.9 倍。
6. **全部使用 v11.5 權重的匯出檔**。延遲與權重無關，但交付權重已改為 v11.5（v5.7 資料集），App 實際要出的組合仍需以該權重重新匯出並重評精度。
7. **FPS 都是模型推論本身的上限**，不含相機取像、前處理、後處理與畫框。
