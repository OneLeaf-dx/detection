## 0. 這份在問什麼

v12.2 在 SM6115 上的結論是：**精度過得了的組合（fp32 ≥ 320）全部太慢，快得起來的組合精度又全部未過。**
那個結論的瓶頸是晶片速度，不是模型——`fp32@320` 的精度已經過線，只差 1.7 倍的速度。

**本計畫只問一件事：在平台 2／3 上，有沒有「精度已知過線」的組合，在突發與持續負載下都 ≤ 40 ms？**

**不回答**的事（事先寫清楚，避免量完之後範圍漂移）：

- **App 要不要做「高階機才開即時辨識」的分級功能**——這是產品決策，由團隊決定。本計畫只提供依據
- **SM6115 的結論**——不重開，維持 S2
- **任何重訓、改權重、改匯出參數**——本計畫只用既有檔案

## 1. 候選組合

**精度與裝置無關**，已在 v12.1／v12.2 量完，本計畫不重量。只有精度已知過線（mAP50 ≥ 0.764）的組合才進候選：

| imgsz | fp32 tflite mAP50 | 過 A（≥ 0.764） | 過 C（逐類跌幅 ≤ 0.10） | SM6115 實測 e2e0 / e2e1 (ms) | 要進 40 ms 需要的加速（e2e0 / e2e1） |
| ---: | ---: | :-: | --- | --- | --- |
| 640 | 0.81554 | ✓ | ✓（PyTorch@640 逐類，最大跌幅 Oily_Spot −0.041） | 277.5 / 266.3 | 7.30× / 6.66× |
| 512 | 0.81361 | ✓ | **未知**（無逐類數據） | 166.9 / 171.7 | 4.39× / 4.29× |
| 416 | 0.79988 | ✓ | **未知**（無逐類數據） | 109.9 / 112.4 | 2.89× / 2.81× |
| 320 | 0.78511 | ✓ | ✓（即參照本身） | 64.8 / 66.4 | 1.71× / 1.66× |

e2e0 的加速倍率以 38 ms 計（40 ms 扣掉 2 ms 後處理保留）。

**待測 8 個檔案**：`last__fp32__i{320,416,512,640}__e2e{0,1}.tflite`。

**不測的**，理由都與裝置無關：

| 組合 | 理由 |
| --- | --- |
| `int8@224/256/288`、`fp32@224` | 精度已未過（最高 0.709），換更快的晶片也不會變準 |
| `int8@320` 以上 | 匯出驗證未通過（`verify.verdict` = 不通過），依量測規範不准進 benchmark |
| `w8a16`、`w8a32` | v12.1 已關（XNNPACK 沒有 INT16 核心；w8a32 只省體積不省時間） |

> **逐類條件 C 對 416／512 的處理**：若這兩者在本平台延遲過線，**先在桌機補量逐類 AP50**
> （與裝置無關，不需手機），補完才下判定。不以「解析度更高應該更準」代替量測。

## 2. 過線標準：v12.2 的三條原樣沿用，另加一條

| # | 條件 | 門檻 | 來源 |
| --- | --- | --- | --- |
| L | 突發延遲 | CPU-only 4T、`num_runs=25`，3 輪交錯取最小 ≤ 40 ms；e2e0 另加 2 ms | v12.2 §2，**不改** |
| A | 精度 | v5.6 test mAP50 ≥ 0.764 | v12.2 §2，**不改**（本平台候選皆已知過線） |
| C | 逐類 | 任一類比 `fp32@320` 低超過 0.10 即否決 | v12.2 §2，**不改** |
| **S** | **持續負載** | **連續 10 段、每段約 30 秒；最後 3 段的平均延遲，每一段都 ≤ 40 ms**（e2e0 另加 2 ms） | **本計畫新增** |

**為什麼要加 S**：L 的協定取三輪最小值，目的正是**排除熱衰減**——那對量「晶片的極限」是對的，
但即時辨識是**持續負載**。高階晶片的降頻幅度通常比 SM6115 大得多，
用突發數字替一個要連續跑的功能下結論，等於答非所問。

**為什麼是「最後 3 段」**：前幾段反映冷機時的突發表現，後段才是降頻之後的穩態。
取最後 3 段而不是只取最後 1 段，是為了不讓單一次背景干擾決定結論；
要求**每一段**都過，而不是平均過，是因為使用者感受到的是最差的那段。

## 3. 量測協定

### 3.1 階段 1：突發延遲（判 L）

- 8 個檔案 × CPU-only 4T × `num_runs=25` × **3 輪交錯**（`tools/run_mobile_benchmark.py --settings cpu --repeat 3`）
- 預估約 15–20 分鐘

### 3.2 階段 2：持續負載（判 S）

- **只量階段 1 過線者中的兩組**：精度最高的一組，以及 320 解析度的一組（若兩者相同就只量一組）。
  階段 1 全未過 → **不跑階段 2，平台 2 直接結案**
- 每組：`--repeat 10 --extra-flags "--min_secs=30 --max_secs=32"`，其餘為標準參數；
  段與段之間只有重啟 benchmark activity 的間隔（`--wait` 設為略大於單段執行時間，避免段間閒置降溫）
- 每段前後以唯讀方式記錄溫度：`dumpsys battery` 的 temperature，與 `/sys/class/thermal/thermal_zone*/temp`
- 兩組之間冷卻到溫度回到階段 1 開始時的 ±2 °C，或至少 10 分鐘，取先到者
- 預估每組約 6 分鐘

### 3.3 階段 3：GPU delegate 與 NNAPI（**需使用者另行確認後才執行**）

依 `Benchmark/AGENTS.md`，啟用 `use_gpu` / `use_nnapi` 屬「需確認」的操作。
**不影響本計畫的判定**（L 與 S 一律以 CPU-only 為準），但專案量測規範要求記錄節點替換率——
SM6115 上兩者都因 `end2end` 的算子被擋而更慢，高階晶片是否不同是要量的，不能推論。

### 3.4 量測條件（每次開量前記錄，不符合的數字不算）

| 項目 | 要求 |
| --- | --- |
| 螢幕 | 常亮、停在桌面 |
| 背景 | 關閉其他 App |
| 電量 | ≥ 50%（經 USB 連線必然充電，**照實記錄**，不嘗試規避） |
| 手機殼 | 記錄有無 |
| 執行緒 | 4（與 SM6115 可比）。平台 2 為 1+3 顆 A715 ＋ 4 顆 A510，4 執行緒的排程落點由系統決定，**本計畫不另測其他執行緒數** |
| 多裝置 | 若 SM6115 同時連線，以 `ANDROID_SERIAL` 指定序號（量測工具預設取第一台） |

## 4. 判定

| 結果 | 判定 |
| --- | --- |
| 有組合 L、A、C、S 全過 | **「平台 2 等級的裝置上，即時辨識成立」**，取其中精度最高者 |
| 有組合 L 過、S 未過 | **不成立**：突發做得到、持續做不到 |
| 階段 1 全未過 | **不成立**，階段 2 不跑 |

**結論的寫法一律分裝置陳述**，不寫成「即時辨識可行」。SM6115 的 S2 結論不因本計畫改變。
平台 3 用同一份判準、同一組候選，量完後兩台並列。

## 5. 為了讓這個標準有效，不准做的事

- **看到結果後改門檻、改段數、改「最後 3 段」的定義**
- **用突發延遲（L）替持續負載（S）下結論**
- **只挑某一輪、某一段的數字報**
- **因為某組差一點，就改測其他執行緒數或其他匯出參數**——那是新問題，要另開一份登記

事後修改紀錄：**判準無修改。** 量測途中補定兩項本文件未指定的細節，均在對應量測開始前 commit：階段 2 的 320 取 e2e1（`384db65`）、兩組間冷卻看 SKIN（`3e620fd`）。詳見結果文件 §5。另有兩處**實作**與 §3.2 的寫法不同，均不涉及判準：持續負載改用 `tools/run_sustained_load.py` 而非 `run_mobile_benchmark.py --repeat 10`（後者的 `all_ms` 會靜默跳過失敗的輪次，「最後 3 段」可能變成別的段，且不記錄溫度）；溫度改讀 `dumpsys thermalservice` 的「Current temperatures from HAL」，因為 `/sys/class/thermal` 在該裝置以 shell 權限讀不到。平台 3 另有兩處實作調整，同樣不涉及判準：溫度感測器改為不分廠牌的名稱比對（`7f6df28`，平台 3 任何量測之前）；SKIN 冷卻規則從第一組就套用。詳見平台 3 結果文件 §6
